# Storage-front protocol and ownership controls

This preparation slice forwards actual HTTP transport through a lease-bound front. It does not replace the normal File storage adapter, register a production endpoint, start a backend or scanner, seed data, or perform financial completion. The source is compiled by the normal solution gate; a separate `HostedStorageFront.Tests` suite retains 128 exact native controls. Existing Quotation capability, companion admission, signing and qualification inventories remain unchanged.

The production constructor requires an independently observed immutable backend. Before and after forwarding it verifies exact Docker generation, image digest, labels, limits, private network, executable hash, init generation and listener inode. The pinned Linux/amd64 fake-gcs-server image is `fsouza/fake-gcs-server@sha256:9e6924ee1b609d9913c3ea836cb4d4a9bc0419cd036ddcd136695720b5713baf` (config ID `sha256:d79ded7272ddc99187d94f61959f37041792e1a79cb3e6d26c9dfb5b845aca21`). The future owner must override its entrypoint to `/bin/fake-gcs-server` and use the exact memory-backend command admitted in source. No persistent mounts or published backend ports are admitted. Registry metadata does not establish executable ownership or readiness.

The front accepts one bounded public RSA bootstrap through an inherited owner pipe. File SDK requests require the actual client socket to belong to the admitted normal File process. Signed invoice reads use the actual public key and V4 verification; fake-gcs-server itself is not signature or expiry proof. Disposal cancels requests and pending bootstrap before releasing shared resources. Every request is bounded by ten seconds, the owner lease and 32 MiB.

Resumable initiation preserves the backend's successful 200/201 session Location while rewriting only its exact origin. Intermediate 308 acknowledgements retain Range without requiring or following Location. Zero-byte PUT probes retain Content-Range. Session escape, unreviewed redirects and malformed/oversized acknowledgements fail closed.

`HostedStorageFrontHost` is a prepared dedicated host, outside normal service startup. Its startup admission requires a clean hosted source, exact executable, immediate owner generation and both inherited pipe ends. The genuine `run_eight_host_financial_acceptance.py` parent caller is a remaining source obligation and is not supplied in this slice. Consequently this slice does not activate that host or claim a usable eight-host launcher. A profile declaration alone never qualifies as resource ownership.

Native HTTP controls run installed Google Storage SDK 5.0.0 and real bounded loopback Kestrel sockets, with explicitly controlled backend/process observers. Pure Docker snapshots, controlled SDK transport, passed counters, a linked InvoiceFile row or preparation receipts do not establish genuine financial acceptance. That requires the admitted eight-source graph, twelve separate actual PostgreSQL databases, real Document rendering, real File storage and immutable scanner database readiness, signed object/generation readback, stable completion replay, no provider sends and verified cleanup.

The CI gate joins all 128 case identities, results, definitions and entries to the normalized test-source inventory. The retained original TRX is `TestResults/StorageFront/storage-front.trx`; no copied or fabricated report stands in for native execution. No deployment, source SQL Server access, cloud storage or provider activation belongs to this candidate.
