# Financial completion evidence preparation

This source prepares the real Accounting full-completion readback and independent File evidence. It does not start a host, provision or seed a database, launch a scanner, send to a provider, or execute financial completion. The separate FinancialCompletionEvidence.Tests project has 102 authored controls; original native reports must pass the exact source-inventory gate before any native validation claim.

AccountingFullCompletionProbe uses the real no-send complete route with the original invoice intent, normal Intranet bearer authorization, operation key and raw capability. It discards the first acknowledgement, reads actual durable completion, requires exactly one total and matching InvoiceFile link, and compares completed replay. Fresh capability and financial/order snapshot callbacks receive the owner cancellation token and have bounded waits. Their actual runtime owners must also observe cancellation and the admitted lease.

The typed Accounting evidence retains its validated PDF SHA256, bucket and object name independently of financial binding. FileObjectCompletionReadback reads a read-only repeatable snapshot from the independently admitted isolated File PostgreSQL database, requires exactly one total and expected Upload and StorageMoveJournal, and checks clean MetadataCommitted state, coordinates and positive generations. Its same-query full Upload/journal/quarantine-intent row fingerprint includes timestamp-only changes during completed replay. File operation IDs are read from actual persistence; they are not assumed equal to Accounting's operation ID.

FileSignedByteReadback accepts only the independently observed literal loopback origin under hosted admission, never a cloud origin. Its normal TLS client disables redirects, proxy, cookies and decompression. The generation-specific response must fit both the actual Upload.Size and ten MiB and match Accounting's PDF digest. The origin owner must be re-observed around transport; a supplied callback alone is not runtime ownership proof. This helper deliberately does not claim quarantine-source absence. That requires an independent owning storage API observation of the admitted source generation.

OwnedGitCommand fixes the core driver's preflight lifetime: all observations and ledger insertion are inside cleanup, stdout/stderr are bounded, EOF precedes finite cleanup, and still-live termination requires the exact observed generation. Unavailable exited-child observations remain null. Terminal observations are retained even when initial observation or ledger insertion fails. Four authored controls use actual finite Git children; their hosted execution remains required.

The outer normal-host owner admits seven explicit task-local HTTPS identities and the separate File HTTP listener. It checks public certificate pins with normal certificate and literal-IP hostname validation, and joins listener inodes to held child handles before and after the handshake. This proves listener readiness only; actual cross-service trust and application health remain caller obligations. Canonical task paths reject traversal and symbolic links, and any additional child-owned listener blocks admission. The expiry signal is deferred across spawn-to-ledger handoff without changing the original lease. Cleanup suspends signal re-entry, releases ownership only after observed exit, and retains exact failure rows plus a five-second cleanup retry when a child cannot safely be stopped. An uncertain process remains preserved and reported; the genuine caller must retain the finite hosted job deadline and verify final cleanup.

The genuine caller still requires a compatible accepted eight-source/dependency graph, actual normal processes, seven HTTPS Production hosts plus the separately admitted File profile, twelve physically distinct PostgreSQL18 databases, isolated Redis for real File idempotency, immutable clamd database/configuration readiness, normal Auth/IAM authority, declared upstream fixtures, the owned front/backend bootstrap, actual PDF and quarantine observations, request/scanner counters, completed replay and verified cleanup. The selected Legacy Auth workload claims currently do not satisfy the selected IAM live guard; this must be resolved by the source owners before activation. No always-allowed authority, synthetic financial/PDF/File response, missing counter interpreted as zero, or TLS bypass qualifies.

This preparation has no deployment, provider, production/schema/source-SQL-Server effect. Pure controls, stable links or destination bytes alone do not establish genuine eight-host financial acceptance.
